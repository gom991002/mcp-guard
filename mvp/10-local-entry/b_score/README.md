## B 점수 방법 (D6-35)

업로드된 논문(『머신러닝 기반 생활체육 참여자의 상해 발생 예측 모델 탐구』)의 절차를 따랐습니다.

| 논문 | 이 스크립트 |
| --- | --- |
| 8:2 층화 분할, 층화 10겹 교차검증 | 같음 (악성 여부 × 생태계로 층화) |
| 클래스 가중치 (전략 A) | 로지스틱 회귀, 악성 가중치 = 정상/악성 비율 |
| PR-AUC 주 지표, AUC-ROC 보조, 부트스트랩 95% 신뢰구간 | 같음 |
| Brier 점수로 보정 확인 | 가중치로 옮겨진 절편을 되돌린 뒤 측정 |
| F1 최대, Youden's J 기준값 교차 확인 | 같음, "지금 규칙의 재현율을 지키는 가장 높은 기준값"을 추가 |
| 순열 변수 중요도, SHAP 기여도 | PFI 10회 반복, 선형 모델의 정확한 SHAP 값(가중치 × 학습 평균과의 차이) |

추가로 정한 것:

- **가중치는 음수가 되지 않습니다.** B 신호는 위험을 올리기만 합니다.
- **기록 전용 신호:** 10개 이상 나왔는데 정상에서 더 자주 나오고, 그 신호로만 잡히는 악성이 없으면 기록만 하고 검토로 올리지 않습니다.
- **판정 방식:** 교차검증에서 모델이 지금 규칙의 재현율을 지키면서 오탐을 10% 이상 줄일 때만 모델이 판정합니다. 아니면 규칙("검토 신호가 하나라도 있으면 검토")이 판정하고, 점수는 보류된 패키지의 우선순위를 매깁니다.
- 위 결정은 학습 데이터에서만 내렸고, 시험 데이터는 결과 보고에 한 번만 썼습니다.

### PyPI 전용 검토 기준 (D6-46)

PyPI의 낮은 재현율을 보완하기 위해 npm의 기준값은 유지하고 PyPI에만 낮은 기준값을 적용합니다. 훈련 데이터의 10겹 교차검증 예측에서 정상 PyPI 보류율을 15% 이하로 제한한 뒤 재현율과 F1이 가장 높은 기준을 골랐습니다. 기본 경로(GuardDog 끔)는 `0.415789`, GuardDog 경로는 `0.464962`입니다. 독립 시험 부분에서 기본 경로의 PyPI 재현율은 28.9%에서 65.1%, 정상 보류율은 15.0%에서 19.4%가 됐습니다. GuardDog 경로는 재현율 81.9%, 정상 보류율 22.5%였습니다. 세부 혼동행렬과 한계는 [pypi_threshold_report.json](data/pypi_threshold_report.json)에 기록합니다. 이 변경은 사후 정책 조정이므로 새 시점 데이터나 실제 설치 표본으로 다시 검증해야 합니다.

| npm 악성 (악의적 의도 / 탈취) | 84% / 83% |
| PyPI 악성 (악의적 의도 / 탈취) | 45% / 0% (5개) |

## 알려진 악성 유사도 (D6-36)

코드 파일마다 지문을 만듭니다. 주석과 공백을 지우고, 문자열·숫자를 자리표시로 바꾸고, 5토큰 묶음의 MinHash(64개)를 계산합니다. 공격자가 C2 주소나 패키지 이름만 바꿔 다시 올린 변종을 같은 코드로 봅니다. 추정 유사도 0.8 이상이면 일치입니다. 색인에는 코드가 아니라 지문만 저장합니다.

| | 결과 |
| --- | --- |
| 시험 데이터에서 지문이 일치한 악성 | 183개 중 53개(29%). npm 악의적 의도 43%, PyPI 26%, 탈취 버전 0% |
| 시험 데이터에서 지문이 일치한 정상 | 230개 중 0개 |
| 규칙이 못 잡았는데 지문이 더 잡은 악성 | 시험 0개 (교차검증에서 "모든 파일" 색인은 4개를 더 잡고 정상 4개를 더 보류) |

- **실제 설치 폴더에서 오탐이 나왔습니다.** "모든 파일" 색인은 진짜 `requests`·`urllib3`·`zod` 파일과 일치했습니다. 유사 이름 악성이 흉내 내는 라이브러리 코드를 통째로 베껴 넣기 때문입니다(예: 악성 `ulthimars`가 `requests` 파일을 그대로 담고 있음). 시험 데이터의 정상 표본에는 그 라이브러리들이 없어 드러나지 않았습니다.
- 그래서 **지문 일치는 검토로 올리지 않고 근거로만 씁니다.** 보류된 패키지의 근거와 LLM 검토 도우미의 참고 자료에 붙습니다.
- 색인은 **Semgrep 신호가 있었던 악성 파일만** 담습니다(악성 800개에서 지문 505개, 544KB). 베껴 넣은 라이브러리 코드와 상용구를 줄이기 위해서입니다.
- **인기 패키지(상위 5,000) 자신의 파일은 비교하지 않습니다.** 베끼는 방향이 악성 → 인기 패키지이기 때문입니다. 이 제외 없이 색인만 쓰면 `requests/__init__.py`가 여전히 걸렸습니다.

## LLM 검토 도우미 (D6-36)

보류된 패키지마다 근거(발견 위치의 코드 조각, 알려진 악성 일치)를 붙여 OpenAI 호환 모델에게 검토자용 요약을 받습니다(`scan --explain`). **판정과 수락을 바꾸지 않습니다.**

**평가 (2026-11-02, [eval_review_assist.py](eval_review_assist.py), 결과 [data/review_assist_report.json](data/review_assist_report.json))**: 무료 로컬 모델 Qwen2.5-Coder 7B(Apache-2.0, Ollama 0.40.13, Docker, CPU 전용)로, 시험 데이터에서 규칙이 보류한 패키지 중 악성 30개·정상 30개를 운영과 같은 근거로 물었습니다.

| | suspicious | unclear | likely_benign (95% CI) |
| --- | --- | --- | --- |
| 악성 30개 | 29 | 1 (형식 위반) | 0 (0–11%) |
| 정상 30개 | 27 | 3 (연결 오류 2, 판단 1) | 0 (0–11%) |

- **이 모델은 보류된 패키지 중 악성과 정상을 가리지 못했습니다.** 정상도 90%를 "suspicious"로 답했고, 이유는 대부분 "`eval` 사용", "외부 프로세스 실행"처럼 이미 신호로 잡힌 사실을 되풀이했습니다. 악성을 "likely_benign"으로 말한 경우는 없어 검토자를 속이지는 않았지만, 검토 부담을 덜어 주지도 못합니다.
- 반면 **알려진 악성 유사도 근거는 같은 표본에서 악성 30개 중 19개에 붙고 정상에는 하나도 붙지 않았습니다.** 보류된 패키지의 우선순위를 정하는 데는 지문 일치가 이 LLM보다 훨씬 쓸모 있습니다(표본이 작아 추정이 거칩니다).
- 한 건에 평균 65초가 걸렸습니다(GPU 없음).
- **v2 프롬프트 재평가 (D6-37, 같은 60개, [data/review_assist_report_v2.json](data/review_assist_report_v2.json)):** 신호를 주지 않는 블라인드 프롬프트와 구조화 점검으로 바꿨더니 더 나빠졌습니다. 악성 30개 중 6개(20%)를 `likely_benign`으로 답해 검토자를 잘못 이끌 수 있게 됐고, 악성 13개는 형식을 어겼으며, 의심도 점수의 ROC-AUC는 0.62였습니다(정상 5개는 연결 오류).
- 결론: 기능은 기본 꺼짐으로 두고, 이 모델로 켜는 것은 권하지 않습니다. 개선 방향은 GPU로 더 큰 모델 쓰기, 정상 비교 근거(같은 파일이 유명 패키지에 있음 등) 함께 주기, 다시 평가하기입니다.

## 한계

- **어떤 신호도 없는 악성은 못 잡습니다.** 재현율 상한이 약 65%입니다. 점수 방식을 바꿔도 못 잡고, 새 신호가 필요합니다. 유사도 색인도 이 상한을 올리지 못했습니다.
- **PyPI가 약합니다.** 악성의 45%만 잡고, 정상 wheel의 약 3분의 1을 보류합니다. 정상 라이브러리도 프로세스 실행·네트워크 호출을 흔히 쓰기 때문입니다. PyPI 탈취 버전은 5개뿐이라 0%라는 수치는 불확실합니다.
- **선택 편향:** Datadog 표본은 주로 자사 규칙(GuardDog)으로 찾은 것이라고 Datadog이 밝힙니다. 그래서 GuardDog식 특정 문자열 규칙(웹훅 주소 등)은 일부러 넣지 않았습니다. 정상 표본은 인기 순위에서 뽑아, 실제로 설치되는 덜 알려진 패키지보다 크고 잘 관리된 쪽으로 치우쳐 있습니다.
- **확률은 실제 위험이 아닙니다.** 학습 데이터의 악성 비율(약 44%)에 맞춰져 있어, 실제 설치에서는 악성이 훨씬 드뭅니다. 점수는 순위로만 읽어야 합니다.
- **분석 공백:** 큰 번들·축소 파일은 Semgrep이 끝까지 분석하지 못하는 경우가 많습니다. 운영에서는 이런 공백이 검토로 갑니다.
- **Windows의 Semgrep 결과가 Docker와 다를 수 있습니다.** 시험 표본 62개 중 정상 2개에서 신호 수가 달랐습니다. Semgrep의 Windows 지원은 베타입니다.
- LLM 검토 도우미 평가는 표본이 60개뿐이고 모델 하나(7B, CPU)만 봤습니다.
- 공격자는 알려진 신호를 피하도록 바뀌므로 주기적으로 다시 학습해야 합니다.
