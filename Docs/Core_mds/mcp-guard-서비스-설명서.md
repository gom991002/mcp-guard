# mcp-guard 서비스 설명서

작성 기준: 2026-11-04 저장소의 설계 문서·코드·테스트·Progress map. 독자: 서비스를 처음 접하는 운영자와 개발자.

이 문서에서 **구현**은 저장소에 실행 코드와 테스트가 있는 경우, **설계**는 도면이나 문서에 정의된 목표, **검증 보류**는 코드가 있어도 실제 클라이언트·클라우드·운영 트래픽에서 확인하지 않은 경우를 뜻한다. 그림의 초록색은 해당 구현 항목의 코드 상태이지 모든 공격의 방어율 100%를 뜻하지 않는다. 우선 기준은 A-01·A-02 도면(`Docs/Core_images/Defense_Paths.png`, `Deployment_map.png`)이다. 다만 사용자가 정한 직접 연결 허용과 M4 승인 방식 등은 `SECURITY.md`의 설계 차이 항목을 따른다.

## 1. 서비스가 하는 일

MCP는 AI 클라이언트가 외부 도구를 찾고 호출하는 연결 방식이다. 도구의 이름·설명·입력 규격과 도구가 돌려준 결과가 모델의 판단에 들어간다. 공격자는 가짜 도구를 진짜처럼 등록하거나, 설명문과 응답에 “다른 지시를 무시하고 정보를 보내라” 같은 명령을 숨길 수 있다.

mcp-guard는 사용자가 **보호 경로를 선택한 MCP 연결** 앞에 놓이는 검사·중계 서비스다. 로컬 경로에서는 stdio 래퍼가, 원격 경로에서는 HTTP 게이트웨이가 도구 목록과 호출을 받는다. 두 경로는 같은 `src/mcp_guard` 판정 모델을 사용한다. 클라이언트가 원 서버에 직접 연결하면 이 검사를 거치지 않는다. 이 프로젝트는 비독점 설정을 택했으므로 직접 연결 자체를 전부 금지하지 않는다.

전체 흐름은 `클라이언트 → 보호 진입(L 또는 C) → 0단계 허가 → 로컬이면 1단계 패키지 확인 → 2단계 도구 등록 확인 → 모델에 보일 도구 → 도구 호출 → 3단계 응답 오염 표시 → 4단계 다음 호출의 전송 목적지·예외 검사`다. 원격 경로에는 단말 설치 패키지가 없으므로 1단계를 적용하지 않는다. 코어가 실패하거나 확인이 필요한 도구면 해당 보호 경로에서 실행을 멈추거나 검토로 보낸다.

## 2. 믿음의 경계와 공격 유형

보호할 것은 사용자의 대화와 파일, 도구 실행 권한, 외부 서비스 토큰, 승인된 도구 정의, 판정·승인·오염 상태 기록이다. 외부 레지스트리·패키지 배포처·원격 MCP 서버·도구 응답은 공격자가 바꾸거나 장악할 수 있는 쪽으로 취급한다. 관리자가 정한 정책과 승인 기록은 더 높은 신뢰를 받지만, 같은 기기 사용자나 실행 중인 게이트웨이 계정이 이를 바꿀 수 있다면 보호 수준이 낮아진다.

- 유형 0, 보호 경로 우회: 클라이언트 설정이 guard 대신 원 서버를 가리키면 검사 자체가 시작되지 않는다. L1–L4와 C1–C3가 보호 경로를 만들고 유지한다. 사용자가 선택한 직접 연결이나 관리 밖 클라이언트까지 구조적으로 막는 것은 현재 범위가 아니다.
- 유형 ①, 도구 위장·가로채기: 악성 서버가 믿을 만한 도구 이름을 베끼거나 비슷한 유니코드 문자·철자로 속인다. 로컬 1단계의 출처·버전·의존성 확인과 2단계 M2 이름 바인딩이 주요 통제다. 이미 승인된 도구와 비슷한 이름은 검토 대상이 된다.
- 유형 ②, 정의 변조: 도구 이름·설명·입력 스키마를 승인 후 바꾸거나 설명문에 다른 도구 호출 지시를 넣는다. 2단계 M3가 승인본과 달라진 정의를 재승인으로 보내고, M5가 민감 설명문을 대체한다. B 문구·구조·분류기 신호는 수상한 설명문을 검토로 올린다. 처음부터 악성인 정의는 변경 검사만으로 잡을 수 없다.
- 유형 ③, 응답 오염: 정상처럼 보이는 도구 결과에 후속 행동 명령을 숨긴다. 3단계 M4가 관측한 결과가 들어온 세션을 오염으로 표시하고, 4단계에서 외부 전송 도구를 감추고 호출도 막는다. B 응답 검사는 감사 신호일 뿐 오염 표시를 결정하지 않는다. 도구 호출 없이 최종 답변만 왜곡하는 공격은 이 봉쇄로 막을 수 없다.
- 범위 밖: 원 서버 자체의 취약점 수정, VM급 격리, 클라이언트 고유의 웹 검색·업로드·다른 커넥터 내용, 보호 경로를 지나지 않은 직접 연결. 로컬 Docker 격리는 별도 보조 트랙이다.

## 3. 판정 원칙: A와 B

A는 허가·거부를 결정하는 규칙이다. 결과는 `allow`(진행), `review`(사람이 승인하거나 재승인할 때까지 보류), `block`(실행 거부)다. B는 위험을 알려 주는 보조 신호이며 코드에서는 `RuleAction.SIGNAL`로 취급한다. B는 `allow`를 `review`로 높일 수 있지만 혼자서 `block`을 만들거나 A의 거부를 풀거나 세션 오염을 지우지 못한다. 그래서 B 분류기가 문장을 놓치더라도 M4의 응답 오염 표시와 외부 전송 봉쇄는 별도로 동작한다.

각 finding·rule에는 `marker`와 `stage`가 있다. M2 같은 도면 ID가 있으면 `M2_`, B 신호는 `B_`, 별도 도면 ID가 없는 A 검사는 `S0_`, `S1_`처럼 단계 번호를 쓴다. L·C는 클라이언트 진입 모듈이지 코어 검사 이름이 아니다. 감사 기록 M1은 어느 경로·사용자·세션·요청에서 어떤 규칙이 작동했는지 이어 볼 수 있게 한다.

## 4. 진입 및 중계 구조

### 4.1 로컬 L1–L4

L1은 서버별 보호 여부를 적은 매니페스트에서 Claude Code `.mcp.json`, hook 설정, Claude Desktop 항목을 만든다. L2 stdio 래퍼는 원 서버보다 먼저 코어를 실행하고, 검사에 실패하면 원 서버를 띄우지 않는 fail-closed 경로다. 원 서버의 `tools/list`를 검사하고 마지막 검사 목록 밖의 `tools/call`을 거부한다. 목록 변경 알림이 오면 예전 목록을 폐기한다. L3는 설정이 바뀌었을 때 보호 항목을 다시 감싸는 재래핑이다. 이는 사용자가 직접 연결을 추가할 자유까지 없애는 강제 수단은 아니다.

L4 Claude Code hook은 MCP 호출 전후와 WebFetch·WebSearch 결과를 관측한다. 관측한 외부 결과로 세션이 오염되면 Bash·PowerShell·WebFetch 등 전송 가능 행동을 막거나 사용자가 미리 지정한 예외에 원문 확인을 요구한다. Claude Desktop 채팅 앱에는 같은 hook이 없어 그 앱의 로컬 대화는 M4 세션 오염·전송 봉쇄 대상이 아니다. Desktop에서도 래퍼를 통과하는 로컬 서버는 1·2단계 검사를 받을 수 있다.

### 4.2 원격 C1–C3

C1은 조직 관리자가 사용자에게 게이트웨이 주소를 커넥터로 배포하는 운영 경로다. 클라이언트별로 다른 경로를 완전히 막을 수 있는지는 확인되지 않았다. C2는 게이트웨이가 자신의 OAuth 서버로 클라이언트를 인증하고 게이트웨이용 토큰을 발급하는 부분이다. 인증 코드·S256 PKCE·클라이언트 등록·회전 refresh token이 구현되어 있다. C3은 원 서버의 자격 증명을 클라이언트 대신 게이트웨이가 보관하고 호출에만 주입한다. 서버별로 공유 자격 증명(`shared`) 또는 사용자별 원 서버 계정 연결(`per_user`)을 쓴다. 사용자별 도구 목록은 다른 사용자에게 재사용하지 않는다.

원격 HTTP 진입은 요청 경로·메서드·본문 크기·Content-Type·Origin·JSON-RPC 형식을 검사한다. 등록된 원 서버를 처음 사용하기 전 운영자 승인 기록을 요구하고, 목록·호출 시 현재 정책과 승인 기록을 다시 대조한다. 실제 `tools/list` 클라이언트는 JSON 또는 요청 범위 SSE의 최종 응답을 읽고 페이지 커서를 따라간다. 공개 목록 캐시는 최대 60초, 사용자별 목록은 사용자 사이에 캐시하지 않는다. `notifications/tools/list_changed`는 캐시를 무효화하고, 민감 도구는 호출 전에 새 목록을 받아 다시 확인한다. `tools/call`은 등록 검사를 호출 직전에 재실행한 뒤 원 서버로 보내며, 원 서버 응답은 클라이언트에 단일 JSON 결과로 전달한다. 중간 스트리밍을 클라이언트로 그대로 중계하는 기능은 현재 범위가 아니다.

## 5. 0단계: 보호 경로와 서버 허가

0단계의 질문은 “이 연결 자체가 관리자가 정한 보호 경로에 있고, 승인된 서버인가?”다. `S0_UNREGISTERED_SERVER`는 관리 목록 밖 서버를, `S0_UNTRUSTED_SOURCE`는 허가되지 않은 등록 출처를 차단한다. 게이트웨이는 서버 식별·설정 승인 기록을 확인한다. 로컬 래퍼는 매니페스트와 자신의 경로를 확인한다. 네트워크 요청에는 WAF 형식 규칙과 IP 요청 횟수 지연 보조 기능도 붙는다. IP 지연은 모든 요청을 세므로 공격 문장인지 정상 대량 작업인지 구별하지 못한다. 반복 지연 시 `429` 제한을 적용하지만 콘텐츠 검사 대신이 아니다.

0단계 허가는 원격 운영자의 실제 코드가 앞으로도 같다는 증명이 아니다. 같은 URL 뒤 서버가 동작만 바꾸면 정의가 동일한 한 이 단계가 알아차리지 못한다. 구성 파일을 디스크에서 바꿨다면 게이트웨이 재시작이 필요한 설정도 있다. 직접 연결은 서비스 바깥이다.

## 6. 1단계: 로컬 설치물 확인, 2-A5

로컬 MCP 서버를 실행하기 전에 공식 Registry의 서버·버전·패키지 목록과 발행자 정책을 확인한다. npm·PyPI 모드에서는 배포 파일의 digest, 로컬 archive, 고정 설치 트리, 실제 실행 파일을 비교한다. 2-A5는 승인한 버전을 고정하고 바뀌면 재승인을 요구한다. 의존성 잠금은 설치된 각 패키지를 공개 배포 archive의 파일과 대조하고 OSV의 악성·취약 기록을 승인 때와 시작할 때 조회한다. 알려진 악성·불일치면 차단하고, 새 릴리스·배포물에 없는 파일·비슷한 패키지 이름·설치 스크립트 등은 검토로 보낸다. Docker 모드는 image와 CLI를 고정하고 Docker Toolkit의 서명 검증을 요구한다. 사설 `local` 모드는 운영자가 고정한 파일 hash를 사용하며 발행자 증명은 없다.

B 코드 행동 검사는 Semgrep CE와 저장소 규칙으로 Python·JavaScript·TypeScript의 알려진 패턴을 찾고, B-score 모델·GuardDog 신호를 보탠다. 발견된 패턴은 검토 사유이지 독자적인 차단 판정이 아니다. 알려진 악성 코드와의 유사도는 근거 기록이며 그 자체로 검토 단계도 올리지 않는다. LLM 검토 도우미는 선택 사항이고 요약이 안전 판정을 바꾸지 않는다. PyPI B-score 문턱값 조정 결과는 저장소의 시험 데이터에 한정된다. 이후 시점의 새 패키지나 실제 설치에서 같은 탐지율을 입증한 것은 아니다.

제한: 설치 스크립트가 생성한 파일과 컴파일된 bytecode의 출처는 완전히 입증할 수 없고, 난독화·동적 로드·native module·Docker image 내부 코드는 Semgrep 범위 밖이다. OSV·Registry·archive 가용성에 의존한다. 기기 사용자가 로컬 승인 파일을 바꿀 수 있다면 자기 승인으로 우회할 수 있다. 실행 직전 hash 확인과 실행 사이에 파일을 교체하는 경쟁 상태도 남는다.

## 7. 2단계: 도구 정의 검사, M2·M3·M5·B

### 7.1 M2 이름과 서버 묶기

서버·도구·namespace가 비면 `M2_EMPTY_*`로 차단한다. 보호한 도구 이름을 믿지 못한 namespace가 등록하면 `M2_PROTECTED_NAME_UNTRUSTED_NAMESPACE`로 차단한다. 보호 이름과 혼동 문자가 같은 이름은 `M2_CONFUSABLE_PROTECTED_NAME`으로 차단한다. 이미 승인한 다른 서버 도구와 모양·철자·구분자·순서가 비슷한 이름은 `M2_LOOKALIKE_TOOL_NAME`으로 검토한다. 이름 형식 권고를 벗어나면 `M2_NONSTANDARD_TOOL_NAME` 검토다. 동명의 다른 서버 도구를 전부 금지하는 방식은 아니다. 핵심은 호출 대상을 “이름만”이 아니라 서버와 함께 묶는 것이다.

### 7.2 M3 정의 변경 감지

도구의 승인된 입력 스키마 hash와 현재 값을 대조한다. 달라지면 `M3_SCHEMA_HASH_CHANGED`, hash가 없으면 `M3_MISSING_SCHEMA_HASH`로 재승인 대상이다. 실조회 목록의 설명문 변경도 재승인 흐름에 연결된다. 기본 승인 주체는 관리자이며 낮은 위험 변경을 사용자에게 맡기는 옵션은 별도 설정이다. 변경 감지는 이미 승인한 기준이 있어야 하므로 최초 승인 자체가 잘못되었을 때의 안전을 보증하지 않는다. 원격 서버가 정의를 그대로 두고 내부 코드만 바꾸면 M3가 이를 볼 수 없다.

### 7.3 M5 설명문 대체·민감 도구 표시

모델이 원 서버의 설명문을 그대로 읽으면 설명문 안의 공격 지시도 함께 읽는다. M5는 민감한 도구의 모델 노출 설명문을 안전한 대체 설명으로 바꾼다. 도구를 세션별로 다루고 전송 가능 도구인지 표시해 4단계 봉쇄에 연결한다. 전송 판별은 관리자 표시를 우선하고 도구 이름·최상위 입력 스키마 이름을 보조로 본다. 이름이나 schema에 단서가 없는 미표시 전송 도구는 놓칠 수 있으므로 운영자의 명시 표시가 중요하다.

### 7.4 B 설명문 검사

문구 규칙은 지시 덮어쓰기, 비밀 수집, 숨긴 지시·다른 도구 지시를 찾는다. 구조 규칙은 같은 서버의 다른 도구 호출을 시키거나 인자를 바꾸거나 사용자보다 우선한다고 주장하는 문장을 찾는다. 선택형 ONNX 분류기는 설명문 전체의 injection 점수를 낸다. 이들이 발견하면 등록은 최대 `review`이며 독자적인 `block`은 없다. 개발 서버는 분류기 옵션을 켜야 하고, 저장소의 Docker 배포 설정은 측정 후 기본 켜짐·기준값 0.86으로 바뀌었다. LLM 설명문 검사는 정상 설명문을 많이 보류한 측정 때문에 기본 꺼짐이다.

저장소의 영어 MCPTox 분할 시험에서 문구+구조는 공격 82.1% 탐지·정상 0.47% 보류, 분류기를 더한 단계식 검사는 95.7%·1.18%였다. 이는 해당 데이터 분할의 결과이고 실제 서비스의 방어율은 아니다. 한국어 자체 제작 300건은 사람 검토 전이며 분류기 단독 공격 탐지 45.3%·정상 보류 2.7%였다. 한국어 검출력을 영어 수치로 대신 설명해서는 안 된다.

## 8. 3단계: 응답 오염, M4·B

원격 게이트웨이가 원 서버 결과를 관측하면 기본적으로 해당 사용자·클라이언트 세션을 오염 상태로 표시한다. 관리자가 `trusted_output`으로 지정한 서버 결과는 오염시키지 않는다. 이는 명시적인 A 신뢰 결정이며, 잘못 지정하면 악성 응답을 받은 세션이 깨끗한 것으로 남을 수 있다. 로컬 Claude Code hook은 MCP 도구·WebFetch·WebSearch 결과를 관측해 오염 표시한다. Claude Desktop 채팅 앱의 로컬 대화는 오염 표시할 hook이 없어 지원 범위 밖이다.

B 응답 문구 규칙과 선택형 분류기는 응답의 수상한 텍스트를 M1 감사 기록에 남긴다. 응답을 고치거나 오염 상태를 켜고 끄는 권한은 없다. 따라서 분류기가 지시를 못 알아보아도 관측한 원 서버 결과가 세션을 오염시키는 A 흐름은 유지된다. 반대로 클라이언트 자체 웹 검색·업로드·guard 밖 커넥터에서 본 내용은 게이트웨이가 관측하지 못한다. 그 내용으로 후속 공격이 일어나도 3단계가 오염을 표시하지 못한다.

원격 세션 구분은 클라이언트별로 다르다. 대화 식별자를 제공하는 경우 이를 쓰고, 제공하지 않는 클라이언트에서는 같은 사용자의 여러 대화가 한 원격 세션을 공유할 수 있다. 새 세션 버튼을 눌렀다면 사용자가 실제로 새 채팅도 열어야 한다. 이전 채팅을 계속하면 그 구분이 내용의 안전을 보장하지 않는다.

## 9. 4단계: 전송 봉쇄·M4 값 정책·3-A4

### 9.1 오염된 세션의 전송 능력 제거

오염 상태의 도구 목록에서는 M5가 전송 가능으로 판별한 MCP 도구를 숨긴다. 목록을 이미 본 모델이 이름을 기억하더라도 호출 직전 재검사에서 거부한다. 이 규칙은 정상적인 업무 전송도 막기 때문에 새 깨끗한 세션에서 다시 수행하거나, 사용자가 미리 지정한 예외를 3-A4로 확인해야 한다. B 점수는 이 차단을 풀지 못한다.

### 9.2 M4 값 정책

값 정책은 세션이 오염되지 않았더라도 **관리자가 설정한 경우 매 호출에서** 전송 목적지를 검사한다. `to`, `cc`, `bcc`, `url`, `webhook`, `visibility` 같은 알려진 입력 이름과 도구별 관리자 지정 경로를 함께 사용한다. 관리자가 허용한 회사 도메인·주소·호스트와 실제 입력을 비교한다. 외부 수신자, 숨은 참조, 허용하지 않은 URL, “누구나 보기” 같은 공개 설정이 걸리면 한 번 쓰는 사용자 승인을 요구한다. 원격 게이트웨이와 로컬 래퍼가 같은 코어 정책을 쓴다.

이 구현은 A-01 도면의 해당 값 “차단” 대신 사용자가 택한 “1회 승인” 방식이다. 값 정책 승인은 오염 세션의 외부 전송 차단을 우회하지 않는다. 관리자가 `m4_value_policy`를 설정하지 않으면 값 검사는 비활성이고, 자유 서술문 속 목적지나 예상하지 못한 필드 이름은 설정만으로 전부 잡지 못한다. 실제 도구의 인자 schema를 보고 필드 경로를 지정해야 한다.

### 9.3 3-A4 예외 승인

오염 세션에서도 사용자가 세션 밖에서 미리 예외로 등록한 도구만 사람에게 물을 수 있다. 현재 원격 경로는 `/approve` 페이지를 사용한다. 요청한 사용자로 로그인하고 원본 인자를 직접 확인한 뒤 승인한다. 요청은 사용자·세션·입력 SHA-256에 묶이고 1회 사용·10분 만료다. 인자가 바뀌면 다시 승인해야 한다. 로컬 경로는 터미널 승인으로 같은 1회 원칙을 사용한다. Claude Code 자체 승인 창의 거절 결과는 hook에 알려지지 않아 거절 감사 기록이 없는 한계가 있다. 승인 화면이나 오류 속 링크는 모델이 먼저 볼 수 있으므로 사용자는 링크만 보고 승인하지 말고 인자 원문을 확인해야 한다.

## 10. 기록·상태·운영 경계

M1은 판정, 원 서버 호출, 오염, 외부 전송, 승인 요청·결정, 세션 재시작, B 점수와 모델 버전 등을 사건으로 기록한다. 선택형 JSONL 감사 파일과 CloudWatch 경로가 있고, 상관 규칙으로 일정 시간의 반복 사건을 묶는다. 감사 기록 실패 시 요청은 계속 진행할 수 있으므로 기록 완전성을 보장하는 차단 경계는 아니다. 접근 권한과 보존 기간은 운영 환경의 실제 설정 검증이 필요하다.

승인·세션·OAuth·원 서버 토큰 상태는 전용 private state 폴더에 둔다. 기본 실행도 해당 폴더를 준비하고 소유권·ACL 및 직계 부모의 쓰기 권한을 확인한다. 감사 파일도 폴더 안에 있어야 한다. 오래된 `.mcp-guard` 상태는 명시적으로 이주해야 시작한다. 이 검사는 파일과 폴더의 보호를 높이지만 이미 같은 실행 계정이 손상되었거나 상위 경로 전체가 안전한지를 입증하지 않는다.

DynamoDB로 세션 오염과 새 세션 카운터를 공유하는 선택 기능이 있다. 테스트는 가짜 서비스로 했고 실제 AWS 호출·IAM·장애 동작은 검증 보류다. 승인 요청·재승인·OAuth와 IP 지연 등은 게이트웨이별 상태라 현재 운영 가정은 게이트웨이 **한 대**다. 단순히 두 대로 늘리면 브라우저 승인 요청과 클라이언트 호출이 서로 다른 상태를 볼 수 있다. `trusted_output` 같은 서버 신뢰 등급은 관리자만 정하며 B 신호가 이를 바꾸지 못한다.

Docker compose와 Caddy HTTPS 구성이 있고 로컬 Docker demo가 종단 흐름을 시험한다. 이는 실제 claude.ai·ChatGPT·Codex·Claude Code·Claude Desktop 접속, 실제 원 서버 OAuth, 클라우드 배포, 장시간 운영을 입증하지 않는다. 설치된 프로그램과 인프라에서 따로 검증해야 한다.

## 11. 공격별 실행 예시

예시 A, 가짜 `send_mail` 등록: 보호 이름을 허가되지 않은 namespace가 등록하면 M2가 차단한다. 철자 하나만 바꾼 이름이면 M2가 검토로 보내고, 원문 설명문에 다른 도구 호출 지시가 있으면 B도 검토 근거를 더한다. 관리자가 잘못 승인했거나 클라이언트가 guard를 우회하면 이 흐름은 적용되지 않는다.

예시 B, 승인 뒤 입력 schema 변경: 새 `tools/list`가 승인된 hash와 다르면 M3가 재승인을 요구하고 그 목록의 호출은 진행하지 않는다. 원 서버의 내부 행동만 달라지고 schema·설명문이 같으면 이 변화는 검출되지 않는다.

예시 C, 검색 결과에 “비밀을 메일로 보내라” 삽입: guard가 그 원 서버 결과를 보면 세션이 오염된다. 다음 목록에서 전송 도구를 빼고, 직접 호출해도 4단계가 막는다. 응답 B 검사가 문장을 분류하는지는 봉쇄 결정에 영향을 주지 않는다. guard가 관측하지 못한 클라이언트 자체 검색 결과라면 이 오염 표시는 생기지 않는다.

예시 D, 깨끗한 세션에서 외부 수신자 추가: 전송 도구와 값 정책이 설정돼 있으면 `to`·`bcc` 값이 관리자 허용 목록 밖인지 확인하고 1회 승인으로 보낸다. 값 정책이 설정되지 않았거나 목적지가 인식하지 못한 필드에 숨으면 검사가 적용되지 않을 수 있다.

예시 E, 새 의존성에 악성 코드: 로컬 시작 전에 lock·배포 파일·OSV·정적 패턴을 확인한다. 알려진 악성 기록이나 파일 불일치는 차단, 의심 패턴은 검토다. 처음부터 승인된 미보고 악성 패키지, 설치 후 생성 파일, 동적 로딩은 놓칠 수 있다.

## 12. MVP 제작 순서와 현재 쓰임

MVP 1 — 정책 엔진 정리: `src/mcp_guard` 공통 데이터 모델과 A 판정 코어, OPA 형식 동등 규칙 초안, Sigma·Semgrep·WAF 규칙 초안을 만들었다. 초안 전체가 실행 엔진에 자동 연결된 것은 아니다.

MVP 2 — 원격 게이트웨이 코어: JSON-RPC `tools/list`·`tools/call` 중계, 등록 판정, M1 사건을 연결한 네트워크 이전 코어다.

MVP 3 — 서버 등록 설정: `servers.json` 읽기, 정책 일치와 중복 활성 도구명 검사, 게이트웨이 설정 생성이다.

MVP 4 — `tools/list` 중계: 실제 HTTP 목록 요청, JSON/SSE 결과, 페이지 커서와 목록 변경 알림, 공개 캐시와 사용자별 분리를 만들었다.

MVP 5 — IP 요청 횟수 지연: 동일 IP·요청 지문에 대한 슬라이딩 창, 지연·반복 제한을 만든 보조 통제다. 프롬프트 인젝션 내용의 탐지기는 아니다.

MVP 6 — HTTP 게이트웨이: 네트워크 진입, edge 검사, live-tools 연결, 승인·재승인 페이지, 상태 저장과 감사·상관 규칙, ASGI 선택 경로를 통합했다.

MVP 7 — `tools/call` 원 서버 중계: 호출 직전 정의 재검사와 실제 HTTP JSON-RPC 호출, JSON/SSE 최종 응답 읽기, redirect 거부를 연결했다.

MVP 8 — 결정 컨트롤: 게이트웨이 토큰과 secret reference, 보호 경로 사용 여부의 예/아니요 분기, M5 설명문 대체를 연결했다. 별도 strict identity 초안은 제거하고 발행자 확인을 1단계로 옮겼다.

MVP 9 — 클라우드 진입: C1 운영 절차, C2 OAuth 서버, C3 공유/사용자별 원 서버 자격 증명, Secrets Manager 선택 저장소, CloudWatch, Docker·Caddy 배포 구성을 추가했다. 실제 외부 서비스 연동은 검증 보류다.

MVP 10 — 로컬 진입: L1–L4 설정 생성·stdio 래퍼·재래핑·Claude Code hook, 1단계 Registry·패키지·의존성 검사, Semgrep·B-score·GuardDog, 선택형 Docker 격리를 구현했다.

MVP 11 — B 분류기: 설명문의 문구·구조·ONNX 신호와 응답 감사 신호, 영어·한국어 평가를 만들었다. Docker 배포 설정은 모델을 기본 활성화하지만 개발 서버는 옵션이 필요하다. 응답 B는 감사용이고 A 판정을 낮추지 않는다.

## 14. 현재 확인할 수 있는 것과 남은 검증

현재 저장소에는 코드·단위/통합 테스트·로컬 Docker 데모가 있다. 이 설명서를 만들면서 `PYTHONPATH=src`로 전체 510개 테스트를 실행한 결과 2개 실패·4개 건너뜀으로 종료되었다. 실패한 두 테스트는 실제 Semgrep 실행 결과를 기대했으나 이 환경의 Semgrep이 JSON 결과 없이 종료 코드 2를 반환해 `B_CODE_SCAN_UNAVAILABLE`이 기록된 경우다. 따라서 이번 실행에서 전체 테스트 통과를 확인했다고 말할 수 없다. 단계 0–4의 보호 경로는 코드로 구현했지만 실제 AI 클라이언트와 원 서버·OAuth 제공자·AWS를 조합한 운영 검증은 남아 있다. 응답 오염 방어는 guard가 실제로 관측한 결과에 한정되고, 답변만 왜곡하는 공격과 클라이언트 자체 기능의 데이터는 막지 못한다. `trusted_output` 오설정, M5 전송 도구 미표시, M4 값 필드 누락, 사용자의 직접 연결은 판단을 바꿀 수 있는 주요 반례다. 적응형 공격을 사용한 단계별 방어율은 아직 측정되지 않았다.

운영 검증의 우선순위는 (1) 실제 클라이언트별 보호 경로와 호출 호환성, (2) 원 서버 OAuth·토큰·승인 화면, (3) 도구별 M5 전송 표시와 M4 입력 경로, (4) 한 대 게이트웨이의 상태·백업·복구, (5) 실제 AWS·감사 보존·장애, (6) 새 공격과 정상 업무 데이터를 분리한 적응형 평가다. 이는 저장소의 미검증 항목에서 정리한 작업 순서이며 측정된 성능 순위가 아니다.

## 15. 용어와 저장소 근거

`tools/list`는 서버가 제공하는 도구 정의 목록, `tools/call`은 특정 도구 실행 요청이다. `taint`는 관측한 외부 결과를 받은 세션에 붙이는 오염 표시다. `review`는 자동 통과가 아닌 사람 확인 대기다. `hash`는 승인 당시 내용과 지금 내용이 같은지 비교하는 지문이다. `fail-closed`는 확인 기능이 실패하면 연결을 진행하지 않는 동작이다. `trusted_output`은 관리자가 원 서버 결과를 오염 표시 대상에서 제외한 신뢰 등급이다.
