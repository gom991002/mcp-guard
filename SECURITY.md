# Security

## Status

This repository is an early scaffold. It is not a production-ready MCP security boundary yet.

Module IDs and the code labelling rule (`marker`, `stage`, code prefix) are defined in [Docs/Core_mds/architecture.md](Docs/Core_mds/architecture.md). When documents disagree, the A-01 and A-02 drawings in [Docs/Core_images](Docs/Core_mds/README.md) win.

Current code covers stages 0-4 on both guarded paths (local stdio wrapper with the Claude Code hook; OAuth-protected remote gateway): entry and admission, stage 1 for local packages, stage 2 registration inspection (M2, M3, M5, B word rules, structural signals and the optional classifier), stage 3 session taint (M4), and stage 4 containment (send blocking, M4 value policy, 3-A4 approvals). It is a portfolio project: the code and tests support these controls, and a local Docker demo exercises them end to end, but no real LLM client, cloud deployment or production traffic has validated them (see Known Limits).

- IP request-rate delay prototype in [mvp/05-indirect-injection-throttle](mvp/05-indirect-injection-throttle/README.md). It counts requests per IP and per IP-plus-header digest in a sliding window held in memory, and computes a capped delay when a limit is exceeded. Defaults come from firewall and WAF services (see its README). It counts all requests, not B/M1/M4 signals, so it cannot tell injection attempts from heavy legitimate use. A key that keeps getting delayed is banned with `429` (5 delays in 10 minutes, 10-minute ban doubling up to 1 hour, after fail2ban, OWASP CRS, and Cloud Armor defaults); IP-only rules are skipped for configured shared egress ranges such as Anthropic's. It is auxiliary and does not replace content inspection.
- HTTP gateway server prototype in [mvp/06-http-gateway-server](mvp/06-http-gateway-server/README.md). It adapts real HTTP requests to the MVP 2 gateway core, handles `OPTIONS /mcp`, maps edge findings to HTTP status codes, and connects the MVP 5 IP delay helper. `--live-tools` connects real upstream list and call clients, checks fetched definitions against reviewed names, descriptions, and hashes, caches public lists for at most 60 seconds, and refreshes named sensitive tools before calls. Unsettled design choices are listed in [mvp/06-http-gateway-server/DECISIONS.md](mvp/06-http-gateway-server/DECISIONS.md).
- Stage 0 configured-upstream admission in [src/mcp_guard/admission.py](src/mcp_guard/admission.py): the MVP 6 server requires a persistent first-use approval record (`--enroll`), then checks the recorded server identity and current policy on each list/call. Changed or newly introduced servers require explicit approval. This binds administrator configuration, not the remote operator or its live code.
- `tools/call` upstream relay prototype in [mvp/07-tools-call-upstream-relay](mvp/07-tools-call-upstream-relay/README.md). It re-runs registration inspection before calls, blocks `review`/`block` tools from reaching upstream, and includes an HTTP JSON-RPC client. MVP 6 `--live-tools` uses that client with the verified live catalog.
- Decision controls in [mvp/08-decision-controls](mvp/08-decision-controls/README.md). They include gateway token issuance/verification, secret-reference token custody, and a yes/no activation branch. The strict identity draft was removed (D6-05): stage 0 and stage 1 already compare names and namespaces, and the publisher check moved to local stage 1 as `trusted_registry_publishers` (`S1_REGISTRY_PUBLISHER_NOT_ALLOWED`; a device user can edit the policy, D6-33). M5 description replacement lives in the core (`src/mcp_guard/m5.py`).
- Cloud entry (C1–C3) in [mvp/09-cloud-entry](mvp/09-cloud-entry/README.md). With `--auth oauth` the gateway is its own OAuth 2.1 authorization server: Protected Resource Metadata, RFC 8414 metadata, Dynamic Client Registration for public clients with an allow-list of redirect URIs, authorization code with mandatory S256 PKCE, single-use 60-second codes, the `iss` response parameter, and rotating refresh tokens stored as hashes. `/mcp` answers `401` with a `resource_metadata` challenge until a gateway token whose audience is this server is presented. Client ID Metadata Documents are accepted from claude.ai, claude.com, and chatgpt.com (ChatGPT and Codex) only, and only when the document allows the `none` token endpoint auth method. ChatGPT's stable and per-server callbacks are on the redirect allow-list. Upstream credentials are chosen per server: `shared` credentials are `env:`/`file:` references injected only by the gateway; `per_user` servers are linked to each user's own upstream account during gateway sign-in (the gateway is an OAuth client of the upstream with PKCE, `resource`, and `iss` checks), and an unlinked user gets a `403 insufficient_scope` step-up. Per-user tokens are kept in a file by default or, with `--upstream-token-store aws-secrets-manager`, in AWS Secrets Manager (one secret per entry, hashed names, access tokens kept in memory when a refresh token exists, SigV4 signed with the standard library); if the store cannot be read, `/mcp` answers `503` and no upstream is called. Per-user tool lists are never cached across users. A missing secret or token fails the upstream call. The server refuses to listen on a non-loopback address without auth. Client IPs come from `X-Forwarded-For` only when the socket peer is a configured trusted proxy. Docker, Caddy, and compose files are included; C1 is documented as an administrator procedure.
- Local entry (L1–L4) in [mvp/10-local-entry](mvp/10-local-entry/README.md). A fail-closed stdio wrapper (L2) loads the core before starting the server, filters `tools/list` results with the same live-registration check the gateway uses, refuses `tools/call` for tools outside the last inspected list, clears that list on `notifications/tools/list_changed`, and ignores spoofed or unsolicited tool lists. A config tool renders Claude Code `.mcp.json`, Claude Code hook settings, and Claude Desktop entries from a per-server guard yes/no manifest (L1, using MVP 8 `decide_activation` for remote entries), and restores guarded entries when a config file changes (L3). A Claude Code hook denies unapproved tools of guarded servers (L4), marks a session tainted when an MCP tool, WebFetch, or WebSearch returns content (`PostToolUse`, session taint store in [src/mcp_guard/taint.py](src/mcp_guard/taint.py)), and in tainted sessions denies Bash, PowerShell, and WebFetch unless the user listed the tool as an exception, which then asks with the raw input. It fails closed when its configuration cannot be loaded. Configuration is non-exclusive: no server allow-list or exclusive managed file is generated. Pending local tool definitions are approved by the service (administrator); users may approve into their own list when the manifest allows it, without overriding the service's entries.
- Stage 1 guarded-local preflight is in [src/mcp_guard/stage1.py](src/mcp_guard/stage1.py) and [mvp/10-local-entry/STAGE1.md](mvp/10-local-entry/STAGE1.md). The wrapper requires an L1 manifest and checks it before starting the child. npm and PyPI modes compare an exact official MCP Registry version and package listing, package-registry release digests, a local archive, a pinned install tree, and the executable. Docker mode pins the catalog and CLI and requires Toolkit gateway signature verification. Private local entries may use explicitly pinned files.
- Unit tests in [tests/](tests/) for the engine, the rule families, and the MVP folders, including end-to-end wrapper tests over real pipes with a fake stdio server.

## Known Limits

- The production package has not yet been verified as a real-client MCP proxy. MVP 6 (with MVP 9 auth) runs either as a standard-library development HTTP server or, with `--server asgi` (D6-28), as a standard-library ASGI app served by uvicorn, the project's only third-party package; MVP 10 is a stdio wrapper. M1 intentionally returns a single JSON result after consuming the upstream JSON or request-scoped SSE final response (D6-29); client-facing streaming and intermediate progress notifications are outside this service's current scope. The Docker image build, a real cloud deployment, and real connections from claude.ai, ChatGPT, Codex, Claude Code, or Claude Desktop have not been tested in this repository.
- Stage 0 admission pins administrator-provided configuration; it does not attest the upstream process or control client routing. The approval store needs filesystem access controls and cannot detect changes to remote behavior behind an unchanged URL. In-process config changes are seen by checks, while edits to config files require a gateway restart to reload.
- Stage 1 npm/PyPI dependency locks (D6-31) compare every installed package with its published npm tarball or PyPI wheel at approval time, check OSV malicious-package records at approval and at every start, and hold releases younger than 30 days, unarchived files, lookalike names, install scripts, and dropped npm provenance for review. They cannot compare files written by install scripts or compiled bytecode (held for review), cannot detect a hijacked release that is older than 30 days and not yet reported to OSV, and the lookalike check covers one-edit, separator, reordering, and ASCII-homograph variants of the 5,000 most popular names per ecosystem only (about 2% of legitimate less-popular names are flagged for review). The PyPI name list is downloaded by each installation; without it the lookalike check holds for review. The OSV lookup and archive downloads are new network dependencies; an OSV outage blocks guarded starts. A user with write access to the manifest and its approval hashes can change what is approved. The preflight hashes files before process launch and cannot eliminate a local file replacement race. Docker image signatures are verified by the Docker CLI at gateway start, not by mcp-guard itself. Public Registry metadata or package metadata outages block new guarded-local starts. A manual `local` source pins bytes but has no publisher attestation. The stage 1 B code-behavior scan (D6-30) runs Semgrep CE as a separate process with this repository's rules only (no Semgrep Registry rules, metrics off). It is on by default (`code_scan.enabled`), does not apply to Docker servers (D6-34), scores each installed package with a model trained on labelled malware (D6-35; on held-out data any review signal catches 65% of malicious packages, 45% for PyPI, and holds about a third of benign PyPI wheels), attaches known-malware similarity matches as evidence that does not raise review (D6-36), records unreadable files (for example ones an antivirus blocked) as gaps, finds only known Python/JavaScript/TypeScript patterns, cannot see obfuscated or dynamically loaded code, native modules, or Docker image contents, and its report and acceptance are local files trusted like the approvals file. Findings hold a start for review; they never block.
- Users may choose a direct origin connection. That connection receives no mcp-guard stage 0–4 inspection. The MVP 8 yes/no decision is wired into MVP 10 client config rendering. Client configuration is deliberately non-exclusive (D6-10, D6-11): users can add other servers, and only Owner-added connectors on claude.ai Team and Enterprise route custom connectors to the gateway. claude.ai directory connectors are allowed as direct connections (D6-09). ChatGPT developer mode, Codex, Gemini Enterprise (administrator-registered confidential client with PKCE), and Gemini CLI can sign in to the gateway (D6-08, D6-26); sessions are kept apart per LLM client and follow ChatGPT's anonymized conversation id where it is sent, while Claude, Gemini, and Codex sessions cover all of a user's conversations in that client, but no way to make ChatGPT or Codex use only the gateway URL has been confirmed. ChatGPT requests share OpenAI egress ranges; unless an operator passes them with `--shared-egress`, IP-only limits count all ChatGPT users together.
- M2 blocks UTS #39 lookalikes of `protected_tool_names` and, since D6-38, sends tool names that imitate another server's approved tool or a protected name (separators/case, word order, one edit) to review. Chosen on 755 real tool names: 0.53% of benign tools held, 88% of generated impersonations caught; added prefixes or suffixes (`my_search`) are not caught, and recall on generated variants is optimistic. It does not apply the bidi step of `bidiSkeleton` or mixed-script checks (non-ASCII names go to review instead).
- In static mode M3 uses a caller-supplied hash. In `--live-tools` mode the gateway computes a deterministic hash from the fetched `inputSchema` and also compares the fetched description with the reviewed configuration. It does not validate the remote operator's code or prevent a server from changing behavior without changing its definition.
- The live catalog is in memory and `--live-tools` is opt-in. Its public cache follows upstream TTL with a 60-second cap; that leaves a window in which silent upstream definition changes may be missed. Private lists are not cached without a trusted authorization context. Notifications invalidate the cache when supported; without them, expiry is the fallback. Network/list failures never authorize a stale tool call, but other upstreams can still list. OAuth-protected upstreams, persistent cache state, and a tool-definition reapproval UI are not implemented. Example hashes in the sample configs are placeholders.
- The B description check is a phrase match. Paraphrased instructions pass it (see [Docs/Core_mds/threat-model.md](Docs/Core_mds/threat-model.md)).
- The optional Horizon Labs classifier (`--b-classifier`, MVP 11) adds a B signal for tool descriptions and an audit-only signal for tool response text. It uses the pinned small model with ONNX Runtime and cached or downloadable weights. It is on by default in the Docker deployment and opt-in for the development server (D6-53); the default review threshold is 0.86. Measured in Docker: about 530 MB of memory and 16 ms per description; on the held-out half of MCPTox, word rules, structural signals and the classifier together caught 95.7% of poisoned descriptions with 1.18% of real ones held; on the unreviewed Korean set v2 it caught 45.3% with 2.7% held. A score never blocks or changes a tool response. Real-client performance has not been validated.
- The downloaded Horizon weights are excluded from Git. On this Windows workstation, ONNX Runtime fails to import because its native DLL does not initialize, so the model was measured inside the Docker image instead. Enabling `--b-classifier` checks the runtime in a child process and refuses startup with an error rather than crashing the gateway process.
- M5 (D6-42, D6-43) is in the core (`src/mcp_guard/m5.py`) and wired into both list paths. A session is sensitive when any listed or approved tool can send data out: the administrator's mark decides, and an unmarked tool whose name or inputs look like sending counts as sending. In a sensitive session tool descriptions and the free text inside input schemas are replaced (local: also server instructions, prompt and resource descriptions; the remote gateway relays only tools). A description that names another server's approved tool is held for review (`M5_DESCRIPTION_NAMES_OTHER_SERVER_TOOL`); on 755 real Docker catalog tools it held none, and its catch rate is not measured (MCPTox poisons tools of the same server). M4 taint and the configured value policy are implemented on supported paths; arbitrary provenance tagging of every response span is not.
- M1 audit events are persisted as JSON Lines only when enabled (gateway `--audit-log`, local manifest `audit_log`). Arguments and results are recorded as SHA-256 digests and sizes. Each event carries a decision model (D6-21): SHA-256 content hashes of the core engine code, the policy and approval files, and the gateway or local entry code, computed at process start. When the optional B classifier runs, M1 records its numeric score, model ID, revision, and decision threshold for tool descriptions (including scores below the threshold) and tool responses. The published model-card default is 0.5; this is a signal threshold, not a logging threshold. The model does not cover runtime state such as stage 0 approvals and session taint, which are separate events. A failed audit write is reported on stderr and the request continues (D6-20), so an audit outage leaves a gap rather than stopping traffic. An allowed tool-list entry is recorded only when first seen or changed. On AWS (D6-22) the gateway sends audit events to CloudWatch Logs in a background thread and keeps the JSON Lines file as the local copy; the CloudWatch sink has been tested only against a fake server. CloudWatch Logs is not WORM storage, and events older than 14 days cannot be sent, so a longer outage leaves them only in the local copy. Audit logs are kept six months (D6-24): the operator sets the CloudWatch log group to 180 days, and the local copy is rotated monthly with months older than 180 days deleted. IAM templates give administrators and readers read access while denying deletion, retention changes, and writes; CloudWatch grants access per log group, so a reader sees every user's events. Tamper evidence stays at that level (no WORM copy), and local endpoint logs are not collected. The correlation rules run every 5 minutes over the last 24 hours and record each match once as a `correlation_alert` event (D6-25); alerts are shown first on a CloudWatch dashboard and then emailed through a metric filter, an alarm, and an SNS email subscription (D6-27); the templates are in `mvp/09-cloud-entry/deploy/alerts` and have not been applied to a real AWS account. Approval refusals at Claude Code prompts are not recorded (accepted limitation, D6-23). The gateway has no stage 3 taint events, and Claude Code approval refusals cannot be recorded because no hook receives the user's answer; approvals are inferred from the tool running. The correlation runner reloads recorded alerts from the local audit copy on restart to suppress repeated matches within the look-back.
- IP delay is a gateway load and abuse-control helper. It is not evidence that a specific response is malicious. It delays a client over its limit and, when the delays keep coming, bans the key with `429` and `Retry-After` (D6-16). The development server sleeps in the request thread, so a flood can pile up waiting threads before a ban; the ASGI server (D6-28) awaits the delay without holding a thread. Counters are per process. The client address is the socket peer, or `X-Forwarded-For` only from `--trusted-proxy` networks, so users behind one proxy or NAT share the IP-only limit.

## Known Divergences From Design

- A-01's M4 value policy describes blocking bcc and external or public destinations. The current implementation follows the user's 2026-11-04 decision to require one-use user approval for a flagged value instead. In a tainted session the independent external-send block still applies; value approval cannot bypass it. The value policy is active only when an administrator configures `m4_value_policy` and only recognizes configured paths or known field names.

- The drawing places Registry namespace verification and 2-A5 pinning on the local package path. The implementation also supports a manual `local` source for private servers because the official public Registry does not list them. This mode has file hashes but no publisher ownership proof. Package modes verify a Registry record and release digest yet cannot prove the installed tree was produced from that archive.
- The configured-upstream approval record is a core-side MVP supplement (design discussion), not a replacement for L1–L4 or C1–C3. Those paths are now MVP 9 and MVP 10, but whether a client actually goes through them depends on how they are deployed (managed files, Owner-added connectors), so stage 0 is not complete for unmanaged machines or individual plans.
- The user's opt-in decision permits direct origin connections outside mcp-guard. A-01/A-02 depict managed paths that prevent direct registration; their blanket client-side enforcement does not apply to the user's chosen direct path (design discussion). This intentional difference is reflected in the architecture and threat model.
- C2 is implemented as gateway-issued tokens (decision D6-02). For `per_user` servers the gateway also obtains each user's upstream token itself (it is the upstream's OAuth client) instead of relaying the client's token; `shared` servers use one credential for all users (D6-12).
- With the default file store, per-user upstream tokens are stored unencrypted with owner-only file permissions. The AWS Secrets Manager store (D6-19) has been tested only against fake Secrets Manager and IMDS servers; real AWS calls, IAM policies, and AWS error formats are unverified. Writes to one secret are held to one per 10 minutes, so a crash can lose a rotated refresh token and force the user to link again. Neither store protects tokens from a compromised running gateway.
- 3-A4 scope is narrowed from irreversible actions (A-01) to tools the user designated in advance as exceptions. In a tainted session M4 removes external-send tools instead of asking for approval (decision D6-07, design discussion); Claude Code asks for `taint_exceptions` through its own prompt, and the remote gateway asks for a user's exceptions on its `/approve` page (D6-49, `--allow-taint-exceptions`).
- Shared egress ranges (Anthropic's two outbound ranges, OpenAI's published ChatGPT list fetched daily) skip the IP-only delay rule only for `/mcp` requests with a valid gateway token; sign-in and token requests from those ranges are still counted per IP. OpenAI's list currently includes one /16 that holds about 95% of its addresses, owner not checked. Gemini Enterprise publishes no list. The daily fetch is tested only against fakes.
- Response attacks on paths mcp-guard cannot observe (D6-52): Claude Desktop's chat app has no hooks, so local MCP servers registered in Desktop get no taint or send blocking; users are told to use Claude in the browser through the gateway and that Desktop's local servers are not covered. Content a client reads by itself (claude.ai web search, uploaded files, connectors outside the gateway) never passes the gateway, so a later gateway send is not blocked. In Claude Code the hook now also denies gateway tools that send data out (`mcp__mcp-guard__*`, D6-42 rule on name and call input) in a locally tainted session.
- Claude, Gemini and Codex send no conversation id, so a signed-in user's remote session spans their conversations and stays tainted. The user starts a new session with a button on `/approve` (signed-in browser and form token); the old session's taint stays on record. The gateway cannot tell which chat continues, so the page and the block message ask the user to open a new chat first; a user who continues the tainted chat after pressing it is exposed again.
- Remote 3-A4 and M4 value-policy approval requests live for 10 minutes in `approval-requests.json` beside other gateway state. Pending and decided requests, including the raw input displayed on the page, survive a restart; a used approval stays used. On POSIX, new writes use mode `0600`. On Windows, the gateway removes inherited ACL entries and grants its runtime account full access before writing input; existing files receive that adjustment at startup. A local ACL check confirmed one explicit runtime-account entry for a newly written file. Pre-existing explicit grants are not removed. The local state folder also inherited Modify rights for other principals; a protected file alone does not prevent a principal with folder write access from replacing it. Operators must restrict both file and state-folder access. Expired inputs are removed on the next guarded tool call, not by a background timer. This follows the user's single-gateway decision and is not a shared store for several gateway processes. A corrupt or unwritable request file fails closed. The link in the tool error is read by the model first; the page approves only for the signed-in user who made the call, with a form token, and the approval is bound to the session and the SHA-256 of the input and used once. Inputs over 4,000 characters are refused instead of shown cut. Not tested against real clients or browsers.
- A dedicated private state folder is required at gateway startup, including when `--state-dir` is omitted. The default is the runtime account's application-state directory; `python -m http_gateway.state_storage` prepares it. Startup checks ownership and access rules on the folder and write-capable entries on its immediate parent, and keeps approval, session, OAuth, and upstream-token files there; an audit log must also be inside it. Explicit state-file paths outside it are rejected. If the old `.mcp-guard` folder contains state, startup stops until setup copies it with `--migrate-from` and records the migration source. Setup rejects links and retains the old copy for operator verification. On Windows, the folder check permits the runtime account, SYSTEM, Administrators, and OWNER RIGHTS. Higher ancestors and a process running as the gateway account remain outside this ACL check.
- A-01 places stage 1 code-behavior analysis on every local package path. The Semgrep scan (D6-30) covers npm/PyPI install trees and pinned `local` files only; Docker images are not scanned and rely on Docker's image signature verification (D6-34).
- The stage 1 review aid (D6-36, `scan --explain`, off by default) sends code excerpts of held packages to the configured OpenAI-compatible endpoint; a non-local endpoint receives third-party code. The code is attacker-written input to the model: its summary is advisory, never changes a verdict or acceptance, and can be manipulated, so a `likely_benign` summary is not evidence of safety. Evaluated with a free local model (Qwen2.5-Coder 7B, CPU), it called 29 of 30 held malicious and 27 of 30 held benign test packages "suspicious": it does not separate them, so enabling it with that model is not recommended.
- Local approval files (manifest, approvals, dependency locks, scan reports) can be changed by the device user, and by malware running as that user, who can then accept findings themselves. This is accepted (D6-33): with non-exclusive, freely distributed clients (D6-10, D6-11) there is no place the user cannot write to anchor a signature check.
- The sending-data hint is shown to the local approver (`approve` note, D6-42); the remote path has no approval screen for it yet, so there it only feeds the M5 sensitivity rule.
- The B description LLM check (D6-44, off by default) sends tool descriptions to the configured OpenAI-compatible endpoint. Evaluated with a free local model (Qwen2.5-Coder 7B) on 99 poisoned and 100 benign descriptions, rules plus the LLM caught 80.8% (rules alone 52.5%) but held 12% of benign ones (95% CI 7–20%), above the 2% bar set beforehand, so it stays off; other models are not measured (D6-44).
- Response-attack containment (M4 taint and the send block) does not cover local MCP servers registered in the Claude Desktop chat app (D6-52, 2026-11-04). Desktop has no hooks, so nothing can mark a Desktop conversation tainted; users are told to use Claude in the browser through the gateway, or Claude Code for local servers. Stage 1 and stage 2 checks still apply to Desktop's guarded local servers through the L2 wrapper. A-01 places M4 on every local path; this is a deliberate scope limit, like the user's direct connection, and the risk remains for anyone who runs local servers in Desktop.
- Trust tiers (D6-54) let an administrator mark a server `trusted_output`, whose results then do not taint a session. This relaxes M4 on the administrator's word (an A decision); a server wrongly marked can carry injected text into a session that stays untainted. B signals cannot set or change a tier.
- Client configuration is non-exclusive (D6-10), so A-01's blanket client-side enforcement is not applied; guarded entries are protected by the wrapper, rewrap, and hook instead.
